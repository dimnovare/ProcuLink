## 1. `T3_suggest_from_source` — source codes ignored, fuzzy guess surfaced instead
**Effort: M · Confidence: 0.90 · Backend**

**Root cause (two compounding defects):**
- **Parser drops source identifiers.** `CxmlOrderParser.cs:117–150` reads only `SupplierPartID`→`BuyerItemCode` (line 146) and **never** reads `ManufacturerPartID` / `SupplierPartAuxiliaryID` / `ManufacturerName`. The `ManufacturerPartNumber` slot already exists on `ParsedOrderLine.cs:32` and `PurchaseOrderLineEntity.cs:40` but is left null — so the Apple MPN (`REDACTED-ORDER-DATA`) etc. are lost at parse time. *(Verified against source.)*
- **Resolution never prefers the source code.** `OrderIngestionService.cs:1061` → `ItemMappingService.ResolveManyAsync` exact-matches `BuyerItemCode` against the learned `item_mappings` table only (`ItemMappingService.cs:60–66`). First order = no learned rows = unresolved → straight to fuzzy catalog AI (`OrderIngestionService.cs:1079–1085` → `BuildCatalogGroundedCandidatesAsync` token-overlap → `OpenAiMappingService` `CatalogBatchSystemPrompt:761–771` forces closest-catalog pick → persists e.g. `ACME-JSON-2` @ 90% at `:1151`). No path prefers the document's own MPN.

**Concrete fix (steps 1–3 minimal; step 4 optional):**
1. In `CxmlOrderParser.cs` ItemOut loop, read `ManufacturerPartID` from `itemDetailEl`; set `ManufacturerPartNumber = NullIfEmpty(...)` on the new `ParsedOrderLine` (144–150). Flows to the entity via `BuildLineEntitiesAsync` — column exists, no migration.
2. In `OrderIngestionService.BuildLineEntitiesAsync` entity loop (1122–1167), **before** reading the AI dict: for each still-unresolved line, check the catalog (`BuildCatalogLookupAsync`, keyed code/barcode/MPN) for an **exact** match on `ManufacturerPartNumber` / raw `BuyerItemCode`. Exact hit → pre-fill `SupplierItemCode`, `resolved=true`, high confidence. No catalog match but source MPN present → surface MPN as the suggestion (`AiSuggestedSupplierItemCode = MPN`, conf ≈ `0.95f`, provenance "source cXML ManufacturerPartID"). Fall through to fuzzy AI only when no usable identifier.
3. Build `unresolvedContexts` (1077–1085) from only lines **not** satisfied by step 2.
4. *(Optional)* Add nullable `ManufacturerPartNumber` to `AiMappingLineContext` (`IAiMappingService.cs:59–64`), thread into prompt + strict JSON schema, instruct model to prefer exact MPN over lexical similarity.

**Risks:** Keep behaviour **byte-identical when no MPN/aux-id is present** to avoid regressing CSV/XLSX/EDIFACT (`OrderServiceCatalogGroundingTests`, `OrderServiceBatchResolveTests`). Pre-filling `SupplierItemCode` flips a line `pending_review`→`ready` — **gate on EXACT catalog hit only**, never fuzzy. Prefer `ManufacturerPartID`; route `SupplierPartAuxiliaryID` to SourceCapture or treat as documented fallback to avoid colliding with a real MPN. Step 4 schema fields must stay additive/back-compat; no-key no-op + allow-list guard (`OpenAiMappingService.cs:829–840`) unaffected.
**Tests:** parser test (MPN→`ParsedOrderLine.ManufacturerPartNumber`); ingestion test (source MPN→catalog pre-fill; no-catalog MPN→0.95 suggestion). Covers both sync `CreateFromFileAsync` and async `ParseStoredFileAsync` (shared `BuildLineEntitiesAsync`).

## 2. `T6_drag_pdf` — drag-to-connect mapper never mounts for PDF orders
**Effort: M · Confidence: 0.78 · Frontend**

**Root cause:** `SpineReview.tsx` latches sub-view to `"triage"` (FixQueueTriage, no drag) whenever `exceptionCount>0` (default at `1737–1740`). PDF orders systematically flag lines `needsReview` → `exceptionCount>0` (`useOrderReview.ts:76–77`). The `MapperWorkbench` drag surface only renders under `subView==="classic"` (`2331–2346` vs `2309`). The mapper's own drag/wire logic and `incomingFromOrder.ts` are **source-agnostic and correct** — the blocker is pure routing.

**Concrete fix:**
- **Primary:** make the drag mapper reachable for PDF/needs-review orders — stop forcing them into Triage-only, OR surface wiring inside/next to `FixQueueTriage`, OR add a one-click "Full document" path (`switchSubView("classic")`) and/or auto-route to classic once `exceptionCount` clears (`SpineReview.tsx` 1737–1740 latch, 2219–2240 toggle, 2309/2331–2346 gates).
- **Secondary co-fix (verified real defect):** in `IncomingPane.tsx` `IncomingRow` (~319 and ~355) the row div (`anchorRef`) and drag-port span (`portRef`) **both** write `sourceEls.current[field.id]` — the parent overwrites the child port so wires anchor wrong. Give the command-palette scroll anchor its own `rowEls` map in `MapperWorkbench.tsx`; let `portRef` be the sole writer of `sourceEls`; repoint deep-link / show-standards handlers to `rowEls`.

**Risks:** Two candidate causes; high confidence the mounted mapper is source-agnostic and the format correlation (PDF→needsReview→triage default→no mapper) cleanly explains "works for some, not PDF." Residual: if the reporter was already in classic "Full document" view and drag still failed, routing fix alone won't suffice — but no PDF-specific break found in the mounted path. **Not live-reproduced** (local branch 11 commits behind `origin/main`; no running app). The `sourceEls` collision is real but secondary/precision.
**Verify:** upload PDF PO with review-flagged lines → reach mapper → drag incoming row onto output field; confirm clean CSV still drags; run mapper vitests.

## 3. `T4_web_search_codes` — external product-code grounding for residual unresolved lines
**Effort: M · Confidence: 0.78 · Backend · NEW CAPABILITY (flag-gated, default OFF)**

**Goal:** optional, provider-neutral web/product search that runs **only** for residual lines (no source code AND no catalog match), feeds a candidate MPN into the existing suggestion flow as an extra `AiMappingCandidate` (provenance-labelled, NeedsReview, never auto-applied).

**Concrete fix (smallest prototype, ~120 LOC + tests):**
- **New seam:** `IProductCodeSearch` in `Core/Services/Ai/` → `Task<ProductCodeMatch?> FindPartNumberAsync(description, brandHint, ct)`; `record ProductCodeMatch(PartNumber, Title?, SourceUrl?, Confidence)`. Returns null when unconfigured.
- **Impl:** `OpenAiProductCodeSearch` in Infrastructure. Reuses **OpenAI 2.10.0 Responses API web_search tool** (`ResponsesClient.CreateResponseAsync`, `ResponseTool.CreateWebSearchTool()`) — **no new dependency, no second vendor key**, reuses `Ai:OpenAI:ApiKey`. Ctor mirrors `OpenAiMappingService.cs:128–148`; no-op (null) when provider≠openai / key blank / flag off. Record tokens via existing `IAiUsageTracker` per-org cap (lines 239–276). null on any failure (mirror `:352–361`).
- **Single integration point:** `OrderIngestionService.BuildCatalogGroundedCandidatesAsync` (~1418), after catalog candidates and before `SuggestSupplierItemCodesAsync` (~1111). Fold a hit as `new AiMappingCandidate(..., IsCatalogProduct:false, Provenance:"web product search: <url>")`. Because `IsCatalogProduct=false`, the existing allow-list (`:829`) still rejects it when a catalog exists → web grounding is additive **only** when there's no authoritative catalog (matches founder intent). No prompt/guard change.
- **Caller gate:** `flag on AND !noEgress` (noEgress at `OrderIngestionService.cs:1094`) AND line has Description AND no source MPN AND no catalog match; cap ~5 lines/order.
- **DI:** register in `Program.cs` (~497) and `Worker/Program.cs`. Config `Ai:OpenAI:ProductSearch:Enabled=false` default.

**Risks:** **Latency + cost** — each call is seconds + billable → bound by flag + per-line cap + per-org token cap. **Data egress** — line description leaves to OpenAI with no EU-residency guarantee → must inherit no-egress org gate + flag, default OFF, or it silently breaks the no-egress guarantee. **Truthfulness** — results plausible not verified → force NeedsReview + honest provenance ("web product search (unverified)"), never auto-apply. **SDK surface (confidence drag)** — `ResponsesClient`/`CreateWebSearchTool` confirmed present in the 2.10.0 DLL by string inspection but **not compiled against**; do a build spike before locking. **Allow-list** — keep `IsCatalogProduct=false` so catalog-backed suppliers still reject web codes (intended).
**Defer (larger build):** dedicated product-data API (Octopart/Icecat/GS1) for verified structured grounding + barcodes; verification round-trip; per-description MPN cache; promote found MPN to first-class suggestion field.

## (1) RANKED TOP-10 "DO THESE"

Ranked by `value ÷ effort`, with irreversible-harm items weighted up. Batches group items one agent can land together (shared files / shared review surface / same test harness).

### 🅰 BATCH A — Backend reliability & money correctness (one .NET agent, jobs/billing/erasure)
*All Low-effort, all backend, all need a real-Postgres concurrency/round-trip test. Highest priority.*

**1. Transform idempotency guard** *(= J1, Critical)*
- **Location:** `ProcuLink.Api/Services/Orders/OrderTransformService.cs:69-355`; enqueued by `TransformOrderJob.cs:38`.
- **Problem:** Retry/concurrent enqueue re-transforms an already-`ready_to_deliver`/`delivered` order → duplicate R2 artifact + duplicate `DeliverOrderJob` dispatch.
- **Fix:** Mirror the parse-path guard — atomic `ExecuteUpdateAsync` flipping `ready`→`transforming` only when still `ready`, assert affected-rows==1; short-circuit if an `OutboundArtifact` already exists. Tighten the `OrdersController:1112` guard to the same atomic transition.
- **Value:** High / **Effort:** Low.

**2. DeliverOrderJob double-retry** *(High)*
- **Location:** `ProcuLink.Api/Jobs/DeliverOrderJob.cs:42`; `DeliveryService.cs:126-169`.
- **Problem:** `[AutomaticRetry(Attempts=3)]` re-runs the whole job when `_fileStorage.DownloadAsync` (L138, unguarded) throws (R2 clock-skew) → orders thrash in `delivering`, can double-dispatch racing the manual retry queue, blows past the dead-letter cap.
- **Fix:** Set `[AutomaticRetry(Attempts=0)]` (matching `RetryDeliveryJob.cs:49`) **and** wrap the download/dispatch so a thrown storage error becomes a failed `DeliveryResult` routed through the single `RetryDeliveryJob` backoff queue. **Both halves required** — the attribute alone strands orders.
- **Value:** High / **Effort:** Low.

**3. Admin-override over-charge** *(= J2, High billing)*
- **Location:** `ProcuLink.Core/Constants/PlanConstants.cs:217-222`.
- **Problem:** else-branch meters against `topTier.Included` (2,500), discarding the admin `effectiveLimit`.
- **Fix:** Use `max(effectiveLimit, topTier.Included)` as the point where pure metering starts; when `effectiveLimit >= topTier.Included` charge `flatEur + over*rate`. Add a test for override > 2,500.
- **Value:** High / **Effort:** Low.

**4. GDPR erase orphans** *(= J3, High data/compliance)*
- **Location:** `ProcuLink.Infrastructure/Services/DataErasureService.cs:36-137`.
- **Problem:** `ai_suggestion_decisions` (with item codes) + `idempotency_keys` survive an order erase.
- **Fix:** Add both to the `RemoveRange` batch (org-scoped: `OrderId == orderId && OrgId == organisationId`), extend the result records with counts, add an erase-completeness test asserting zero rows remain.
- **Value:** High / **Effort:** Low.

**5. AI usage/quota lost-update** *(High billing-integrity)*
- **Location:** `ProcuLink.Infrastructure/Services/AiUsageTracker.cs:68-97`.
- **Problem:** read-modify-write absolute `UPDATE` → concurrent increments under-count the meter; first-use insert race throws an uncaught 23505.
- **Fix:** `ExecuteUpdateAsync(s => s.SetProperty(u => u.TokensUsed, u => u.TokensUsed + tokens))`; wrap insert in a 23505 catch falling back to the atomic update (mirror `SchemaFingerprintService.RecoverFromConcurrentInsertAsync`). Add a parallel-increment Postgres test.
- **Value:** High / **Effort:** Low.

> **Batch A rationale:** five Low-effort backend fixes, all sharing the same review lens (idempotency/atomicity/erasure-completeness) and the same test infra (real-Postgres Testcontainers, per the "InMemory masks Postgres FK" memory). One agent, one PR, one `/code-review`. **This batch is the launch-blocker set.**

### 🅱 BATCH B — Hot-path query cost (one .NET agent, dashboard/buyers read paths)
*Both Low-effort, both the identical anti-pattern, both behavior-preserving via the existing indexed `BuyerName` column.*

**6. Dashboard topology full-table jsonb fetch** *(High perf)*
- **Location:** `ProcuLink.Api/Controllers/DashboardController.cs:102-156`.
- **Problem:** Landing-page query loads **every** order's full `CanonicalJson` blob and parses each in a loop just to extract `buyerName`. Unbounded; grows with order history.
- **Fix:** Drop `CanonicalJson` from the `Select`; read the indexed `BuyerName` column (fall back to JSON only for null rows). Aggregate buyer/wire counts in SQL where possible.

**7. BuyerService full-table jsonb scan** *(High perf)*
- **Location:** `ProcuLink.Infrastructure/Services/BuyerService.cs:25-62`.
- **Problem:** Same anti-pattern for the Buyers list — loads all `CanonicalJson` to count orders per buyer.
- **Fix:** SQL `GROUP BY` over the indexed `BuyerName` column for count + `Max(CreatedAt)`; CanonicalJson fallback only for null-BuyerName rows.

> **Batch B rationale:** identical root cause, identical fix idiom, adjacent files. The stale "follows ListPagedAsync pattern" comment on the dashboard is false — fix the comment too. One agent.

### 🅲 BATCH C — Primary daily-action UX on the money-maker (one frontend agent, mapping/inbox)
*The two highest-value UX findings — both on the screens a coordinator hits every single upload.*

**8. Two overlapping "Accept all" buttons** *(P1, high)*
- **Location:** `project-proculink/src/components/bridge/MagicMappingPreview.tsx:713-785`.
- **Problem:** Two near-identical bulk-accept buttons (purple client-side "Accept all AI suggestions (N)" + green server-side "Accept all high-confidence (N)") with overlapping scopes and contradicting counts — reads as a bug on the most-repeated action.
- **Fix:** Collapse to ONE primary "Accept all suggestions"; demote high-confidence to a secondary `≥85%` toggle/dropdown. Unify to the server path so it persists without a separate Commit. Label by what they DO, not "accept all."
- **Value:** high / **Effort:** S.

**9. Inbox "Send selected" fires /redeliver on non-deliverable rows** *(P1, high)*
- **Location:** `project-proculink/src/components/bridge/InboxView.tsx:577-611,628,852-893`.

- **Value:** high / **Effort:** M.

### 🅳 BATCH D — Public honesty + infra defense-in-depth (one mixed agent, small + targeted)
*Two genuinely actionable items pulled up from the unverified list — both Low-effort, both real.*

**10. ForwardedHeaders + support-form rate limit** *(P2 security, Low)*
- **Location:** `ProcuLink.Api/Program.cs:213-267,756-760`; `TenantResolutionMiddleware.cs:205-224`; `SupportController.cs:24-59`.
- **Problem:** No `UseForwardedHeaders()` → behind Railway every anonymous caller shares the **proxy IP** partition, collapsing the webhook (120/min) + global (300/min) buckets into one (one abuser DoSes all webhook senders) and gutting the trial-farming IP axis. The anonymous `POST /api/support/contact` has no named limit and feeds an email sender (amplification/cost vector).
- **Fix:** Add `ForwardedHeadersOptions` (XForwardedFor|Proto, `ForwardLimit=1`, restricted to the Railway edge) + `app.UseForwardedHeaders()` as the first middleware; add a tight `"support"` policy (`5/60s`) + `[EnableRateLimiting("support")]`; confirm `MailKitEmailSender` keeps user input out of headers (CR/LF strip).
- **Value:** Restores per-source rate limiting on the entire unauthenticated surface + the anti-farming guard. / **Effort:** Low (~10 lines + one policy + a deployed-request check).

# ProcuLink — Program Design (2026-06-08)

_8-agent parallel deep-design. Source of truth for the heart-piece flexible-mapping rework + 7 strategic initiatives. Read before building._


## heart-piece-flex — effort XL

**Area:** Per-order editable canonical mapping on the order-review screen (SpineReview): add/remove custom canonical fields, per-order output-mapping overrides, interactive drag-to-connect on the existing SVG overlay, and a Scriban-style power-user manipulate editor reusing the FieldManipulator infrastructure.

**Design:** "Introduce a PER-ORDER mapping/override layer that sits BETWEEN the fixed canonical model and the fixed output transforms, WITHOUT changing the proven parse→canonical→deliver path. Three additive concepts, all stored in the existing purchase_orders.canonical_json jsonb (no new table needed for v1): (1) CUSTOM CANONICAL FIELDS — a list of user-added {key,label,scope:header|line,value or per-line values} kept under a new canonical_json node `customFields`; they never touch the typed columns, so existing parsers/transforms are untouched. (2) PER-ORDER OUTPUT MAPPING OVERRIDE — an OutputMappingConfig (canonical-field → output-field-path + optional ManipulatorEntry[]) stored under canonical_json node `outputOverride`, reusing the EXISTING ManipulatorEntry/ManipulatorRegistry model verbatim (this is the 'Scriban-style manipulate' surface — no new templating engine, honouring the founder's no-new-bug / reuse rule). (3) A new TEMPLATED output transform path: a single new MappedTransformService that, WHEN an order has an outputOverride, builds the output document from the override (canonical values + customFields, run through ManipulatorRegistry) instead of the fixed columns — for the formats where an override makes sense (start with CSV + JSON, the two flat formats). Default behaviour (no override) = byte-for-byte the current fixed transforms, so nothing regresses. Drag-to-connect KEEPS the CSS-grid+SVG overlay: add a thin interaction layer (a pointer-events-enabled hit-circle at each existing measured endpoint + a drag-ghost path) that, on drop, edits the in-memory override map and persists via the resolve/override endpoint — NO React Flow / dnd-kit. The power-user editor is a disclosure panel (Cmd+K / 'Edit mapping manually' toggle, per the one-great-experience + standards-visibility rules) that exposes the same outputOverride as an editable table of {canonicalField → outputPath, manipulators[]} rows, with a live preview calling a new dry-run preview endpoint."

**Phasing:**
1. Phase 1 (smallest, backend-only, invisible): add OrderMappingOverride Core model + IOrderMappingOverrideService + GET/PUT /api/orders/{id}/mapping-override (canonical_json writes, org-scoped, manipulator-type validation). Ship with tests; no UI, no transform behaviour change. Proves storage + round-trip safely.
2. Phase 2 (output override read path, default off): add MappedTransformService (CSV+JSON) and the override-aware branch in OrderTransformService.TransformAsync that only activates when an override exists. Add the regression test proving no-override output is byte-identical. Still no UI — operators could set an override via API and see it honoured.
3. Phase 3 (preview + manual power-user editor): add POST /preview endpoint and the OutputMappingEditor.tsx disclosure panel (manipulator rows + live preview), surfaced behind Cmd+K / a toggle. This delivers the 'map & manipulate manually' value with full visibility before anything is saved.
4. Phase 4 (custom fields in the spine): extend buildNodesFromOrder + add the '+ Add field' / remove affordances, persisting via the Phase-1 endpoint and rendering custom fields in OutputPreview. Header-scope first, then line-scope columns.
5. Phase 5 (drag-to-connect interactivity): add the optional interactive hit-circles + drag-ghost to SpineConnectors.tsx and wire onConnect → override edit. Last because it is the highest-touch UI change and depends on the override model + persistence from Phases 1-4 being solid.
6. Phase 6 (optional hardening): if usage warrants, promote the jsonb override to a dedicated order_mapping_overrides table (additive migration), extend MappedTransformService to XML/UBL/cXML/X12, and add per-supplier default overrides that seed per-order ones.

**Risks:**
- Output correctness regression: the override-aware branch must fall through to the EXACT existing transformer when no override is present. Mitigate with the byte-identical regression test in Phase 2 and a strict 'override exists AND format supported' guard; never let an empty/partial override silently drop required fields (keep the NeedsReview / null-SupplierItemCode validation that CsvTransformService.cs:51-61 enforces).
- Power-user manipulator abuse / injection: a hand-typed ManipulatorEntry.Type or bad params could throw at transform time (ManipulatorRegistry.Resolve throws on unknown type, manipulator ctors throw on bad params). Validate every rule at PUT time by attempting Resolve()+a dry Apply() and return 400 — fail at edit time, never at deliver time.
- canonical_json merge hazard: there is already a documented denormalisation split (buyer_name column vs canonical_json, per MEMORY). Writing overrides into canonical_json must use ONE shared merge helper (extract MergeCanonicalJson from OrderResolutionService.cs:171-202) so override writes never clobber buyerName/enrichment keys, and reads tolerate absent keys.
- offer⇔works: do NOT expose UI for unsupported formats. v1 MappedTransformService handles CSV+JSON only; the manual editor + drag UI must hide or disable override controls for XML/UBL/cXML/X12 until Phase 6, otherwise the UI promises a transform that won't happen.
- Custom fields must not leak into delivery as fake canonical data: they live only in canonical_json + (optionally) the override-driven output; they must never be written to typed columns or trip the resolve send-guard. Keep them out of the NeedsReview computation.
- Drag interaction perf/measurement: SpineConnectors already double-rAFs and ResizeObserves to keep wires aligned (lines 113-166); adding interactive hit targets must not break that measurement loop or introduce pointer-capture leaks. Keep base overlay pointerEvents:'none' and opt-in only the hit-circles.
- Concurrent-chips / shared-dir hazard (per MEMORY): no EF migration in v1 avoids snapshot races; if Phase 6 adds a table, isolate the migration and add Ignore<>() in every InMemory test builder to avoid the 48-failure class seen before.

**Open questions:**
- Scope of 'output mapping on the fly': is the target per-ORDER only (this delivery), or should a per-order override be promotable to the supplier's default (writing back into SupplierPoMapping/a new supplier-output-mapping)? The plan assumes per-order in canonical_json; supplier-default write-back is a clean Phase-6 add but changes the data model.
- Which output formats must support overrides at launch? v1 proposes CSV+JSON (flat, low-risk). Do the first pilots actually need XML/cXML/EDIFACT/X12 field-level overrides, or is column reordering/renaming on CSV the real wedge?
- For 'add a canonical field the parser missed' — does it need to flow into the DELIVERED file (output override picks it up), or only be visible/recorded on the review screen + audit? The plan supports both via outputOverride referencing a customField, but the founder may only need display+audit initially.
- Custom LINE fields: do suppliers need per-line custom values (e.g. a GLN per line) or only per-order header extras? Per-line is supported in the model (LineValues map) but adds material UI complexity in the subnode rows — confirm before Phase 4.
- Should the manual editor expose RAW canonical_json / a true free-text expression (closest to literal 'Scriban'), or is the constrained {field→path + manipulator chips} model sufficient? The constrained model is far safer (validated, no arbitrary code) and reuses existing infra; a free-text mini-language would be a separate, larger build.
- Does drag-to-connect need to create NEW canonical↔output links, or only re-point existing ones? Creating arbitrary new output paths needs an output-path schema per format; re-pointing within a known schema is much smaller.

## cross-org-library — effort L

**Area:** Cross-org (anonymized, opt-in) shared mapping suggestion library — the network-effect moat. Backend: ProcuLink-waved (.NET 8 / EF Core / Postgres). Frontend: project-proculink (Next.js 15).

**Design:** Add an opt-in, anonymized, cross-org SUGGESTION layer that sits strictly BETWEEN deterministic resolve and the AI call, never touching the proven parse→canonical→transform→deliver path. Core idea: aggregate only the (buyer_code_normalized, description_token_hash) → supplier_code statistic across opted-in orgs, with NO org id, NO supplier name, NO raw counts that can fingerprint a single org. Privacy model (defense-in-depth): (1) Contribution requires Organisation.MappingLibraryEnabled=true AND the org is NOT no-egress (SelfHostedOcr) — reuse the existing opt-in/no-egress gate plumbing. (2) The shared table stores normalized buyer_code (trim+lowercase), a salted hash of the description if present, the SUGGESTED supplier_code value, and an aggregate observation_count + distinct_org_count — it never stores OrgId, SupplierId, or supplier name. (3) k-anonymity threshold: a row is only ever READ/served when distinct_org_count >= K (start K=3) — so a suggestion can never echo a single org's private mapping back to a competitor; below K the row exists only as a counter and is invisible. (4) Buyer item codes alone are weak PII but supplier codes can be a customer's private catalog — so the served value is supplier_code only when >=K orgs independently agreed on the SAME (buyer_code→supplier_code) pair (consensus), which both raises quality and makes single-org reconstruction impossible. (5) Contribution is on CONFIRMED resolutions only (UpsertAsync with MappingSource.Manual / ai_accepted), not raw parses, so we aggregate human-verified truth. Integration: introduce ISharedMappingLibrary with Contribute(...) and SuggestMany(buyerCodes,...) (org-agnostic — takes no SupplierId because the library is supplier-name-blind). In BuildLineEntitiesAsync, after ResolveManyAsync and BEFORE the OpenAI call, for opted-in non-no-egress orgs query the library for the unresolved buyer codes; any consensus hit (>=K, >=min-confidence) becomes an AiMappingSuggestion with Provenance='community' / Confidence derived from consensus ratio — surfaced as a suggestion ONLY (never auto-applied, identical handling to today's AI suggestions). Contribution is wired into ItemMappingService.UpsertAsync (the existing confirmed-mapping chokepoint) as an awaited best-effort write to the shared table, behind the opt-in flag. Gate the whole feature on the dormant BillingFeature.MappingLibrary so it ships dark and is enabled per-tier later. The library is a SUGGESTION SOURCE, peer to OpenAI — it does not change resolve/transform/deliver semantics, so there is zero new failure mode on the happy path.

## partitioning — effort L

**Area:** Backend / Postgres data lifecycle — declarative time-partitioning + retention for append-only tables (audit_events, po_passport_events, delivery_attempts) and a deliberate carve-out for idempotency_keys

**Design:** Two-track plan that honours offer<->works and keeps the parse->transform->deliver path untouched. TRACK A (do first, near-zero risk): turn on the EXISTING retention sweep — it is shipped, safe-off, and is the cheaper 80% win for 'grows unbounded'. TRACK B (do later, at the 100-customer / multi-instance horizon): native Postgres RANGE declarative partitioning by month for the three true append-only tables (audit_events, po_passport_events, delivery_attempts) ONLY. Explicitly DO NOT partition idempotency_keys (composite (OrgId,Key) PK + timestamp-less lookup make it a correctness+perf hazard; its 48h sweep already keeps it tiny). For Track B, the partition key is the existing prune timestamp (created_at / occurred_at / attempted_at); the surrogate Guid PK becomes composite (id, <ts>) which Postgres requires and which no read path depends on. Because EF 8/Npgsql 8 have no partitioning API, all DDL is raw migrationBuilder.Sql and EF is kept UNAWARE of the children: the C# model/snapshot continues to describe a single logical table, and we add an EF model annotation only if needed to suppress drift on the PK change. The unsafe part — converting an already-populated table — is solved with the online 'rename + create-partitioned-parent + attach old data as a bounded catch-all partition' pattern executed OUT-OF-BAND (not inside the fire-and-forget startup MigrateAsync), so there is no long copy on the deploy path and no downtime. Future monthly partitions are pre-created by a new tiny Hangfire job in the existing Worker (no pg_partman/pg_cron dependency, Neon-plan-agnostic). The retention sweep coexists unchanged: on a partitioned table its bounded ExecuteDelete still works, and once partitioned, retention can additionally/instead DROP whole past-window partitions (instant, no row-by-row delete, no bloat) — a later optional optimization inside DataRetentionService gated behind a flag. Net: smallest-safe-first, no new bugs, no UI surface (this is pure infra; nothing to over-claim).

## peppol-wedge — effort L

**Area:** Peppol / e-invoice (BIS Billing 3.0) compliance wedge — UBL invoice generation + validation in-house, AS4/Peppol network transport partner-wrapped (Storecove/Tickstar)

**Design:** Pursue a two-track wedge that respects the founder's offer<->works and partner-wrap rules. Track A (ProcuLink builds, sells immediately): produce and validate a genuinely BIS Billing 3.0 / EN 16931 compliant UBL invoice document. ## sso-saml — effort M

## test-data-gen — effort L

**Area:** Edge-case order generation + bulk-upload test harness for all 7 PO formats (parse→canonical→transform→deliver)

**Design:** Build a two-tier edge-case test rig that reuses the EXISTING proven format builders. Tier 1 (offline, fast, deterministic): a .NET console project `ProcuLink.EdgeGen` that emits a corpus of N edge-case order files across all 7 formats into `.live-fixtures/<format>/<case-id>.<ext>`, each paired with a sidecar `<case-id>.expected.json` declaring the intended outcome bucket (parse_ok_ready | parse_ok_review | parse_failed) and a few invariant assertions (e.g. expectedLineCount, expectedPoNumber, mustFlagReview). The generator is parameter-driven over a single case matrix so one adversarial dimension (missing field, zero/negative qty, huge line count, multi-currency, encoding, thousands-separators, duplicate PO, malformed header, unicode) is expanded across every applicable format. It reuses the production parsers in-process to self-verify each generated file lands in its declared bucket BEFORE it is written — so the corpus is guaranteed meaningful (no silently-broken fixtures) and Tier 1 doubles as a pure parse-layer regression suite with zero network. Tier 2 (live): a TypeScript harness `scripts/bulk-edge-upload.mjs` in project-proculink that walks `.live-fixtures/`, uploads each file via the proven Clerk-token multipart recipe to /api/orders/upload (sequential, throttled to respect the upload rate-limiter and Pilot supplier cap by reusing one supplier id), polls GET /api/orders/{id} until terminal, and writes a results CSV/JSON (case-id, format, http status, final order status, line count, needs-review count, error) plus a console summary of declared-vs-actual mismatches. PDFs split: text-layer PDFs are generated programmatically (reuse PdfOrderParserTests.CreatePdf logic); scanned/textless PDFs are a SEPARATE founder-supplied folder `.live-fixtures/pdf-scanned/` (offer⇔works: do not synthesize fake scans — flag them as requiring real OCR/vision and real documents). The harness never mutates production beyond creating orders under one test supplier; no new product code paths, no UI — keeps the proven path intact.

**Risks:**
- Live runs against prod create real orders under the org and consume the Pilot/plan order quota (CheckOrderLimitAsync returns 429 at cap, OrdersController.cs:144-155). Mitigate: run bulk against LOCAL first; on prod use a dedicated test org or accept quota burn and a cleanup pass; harness must handle 429 gracefully and stop.
- Upload rate-limiter ('upload' EnableRateLimiting, OrdersController.cs:78) will throttle bulk uploads — harness MUST be sequential with backoff, not parallel, or it will see spurious 429s mistaken for failures.
- Pilot cap = 1 supplier — all fixtures must target ONE reused supplierId; cannot create a supplier per format (memory live-format-testing).
- XLSX fixtures MUST be ClosedXML-generated; openpyxl/other zip-deflate variants fail on Linux .NET in prod but pass locally — a fixture artifact that would produce false 'failed' results.
- Scanned/textless PDFs CANNOT be meaningfully synthesized (no text layer to fake); attempting to generate them risks an offer⇔works violation (claiming OCR coverage that the corpus doesn't truly exercise). Must be real founder PDFs.
- Self-verification couples EdgeGen to current parser behaviour — if a parser is intentionally changed, expected.json sidecars need regeneration; keep generation deterministic and re-runnable.
- Unicode/encoding fixtures (UTF-8 BOM, UTF-16, Latin-1, CP1252) interact with each parser's StreamReader detectEncodingFromByteOrderMarks settings differently — must verify per-format rather than assume uniform handling.
- Huge-line-count fixtures may exceed the 10MB upload cap (returns 413) before they exercise parse perf — size them deliberately under the cap, or test the cap explicitly as its own case.

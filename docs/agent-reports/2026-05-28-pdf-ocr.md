## Design decisions

### 1. Provider-neutral interface in Core
`IDocumentOcrService` lives in `ProcuLink.Core.Services.Ocr` so any project layer
can depend on the abstraction without a direct Infrastructure reference. Mirrors
how `IAiMappingService` and `ISchemaInferencer` are placed.

### 2. Opt-in pattern (no-op when keys absent)
Mirrors `OpenAiMappingService` and `OpenAiSchemaInferencer`: the constructor checks
for both `Ocr:Azure:Endpoint` and `Ocr:Azure:ApiKey`; if either is missing the
`DocumentIntelligenceClient` is never constructed and `IsAvailable` returns `false`.
`ExtractTextAsync` returns `string.Empty` immediately on the no-op path.

### 3. prebuilt-read model
Chosen over `prebuilt-layout` or `prebuilt-document`:
- `prebuilt-read` extracts plain text from PDFs and images at the lowest token cost.
- Layout and form-field understanding are not needed for the OCR fallback — the
  existing `PdfOrderParser` line-parsing logic runs on top of the extracted text.

### 4. 30-second hard timeout
Matches the timeout pattern in `OpenAiSchemaInferencer.CompleteWithTimeoutAsync`.
`CancellationTokenSource.CreateLinkedTokenSource(ct, timeoutCts.Token)` where
`timeoutCts` is cancelled after 30 s. An `OperationCanceledException` from timeout
(not from the caller's `ct`) is caught and logged as a warning; empty string is returned.

### 5. Fail-safe exception handling
All exceptions are caught at the outermost `try/catch`, logged as `LogWarning`,
and swallowed. The service never throws to callers — the OCR fallback must not
break the main parse pipeline.

### 6. NoOpOcrService for DI
Rather than registering a nullable `IDocumentOcrService?`, the DI container always
has a concrete implementation. When keys are absent, `NoOpOcrService` is registered
so `PdfOrderParser` (and any future caller) never needs null-guard code.

## DI registrations needed

Add to `ProcuLink.Api/Program.cs` (and `ProcuLink.Worker/Program.cs`) after the
existing AI service registrations:

```csharp
// OCR fallback — opt-in via Ocr:Azure:Endpoint + Ocr:Azure:ApiKey
var ocrEndpoint = builder.Configuration["Ocr:Azure:Endpoint"];
var ocrApiKey   = builder.Configuration["Ocr:Azure:ApiKey"];

if (!string.IsNullOrWhiteSpace(ocrEndpoint) && !string.IsNullOrWhiteSpace(ocrApiKey))
{
    builder.Services.AddSingleton<IDocumentOcrService, AzureDocumentIntelligenceOcrService>();
}
else
{
    builder.Services.AddSingleton<IDocumentOcrService, NoOpOcrService>();
}
```

Both `AzureDocumentIntelligenceOcrService` and `NoOpOcrService` are stateless after
construction and safe to register as singletons.

## Config keys

| Key | Where | Example |
|---|---|---|
| `Ocr:Azure:Endpoint` | `appsettings.Development.json` / Railway env | `https://my-resource.cognitiveservices.azure.com/` |
| `Ocr:Azure:ApiKey` | gitignored local secrets / Railway env | 32-char hex key from Azure portal |

Add to `appsettings.Development.json` under the existing `Ai` block:

```json
"Ocr": {
  "Azure": {
    "Endpoint": "",
    "ApiKey": ""
  }
}
```

Leave both empty in development to stay on the `NoOpOcrService` path (safe default).

## How PdfOrderParser should call this service (follow-up wiring)

`PdfOrderParser` currently uses PdfPig to extract text. The OCR service should be
called as a fallback when PdfPig returns an empty or near-empty text result:

```csharp
// In PdfOrderParser — inject IDocumentOcrService via constructor
private readonly IDocumentOcrService _ocrService;

// In ParseAsync / the text-extraction step:
var text = ExtractTextWithPdfPig(stream);

if (string.IsNullOrWhiteSpace(text) && _ocrService.IsAvailable)
{
    stream.Position = 0; // rewind after PdfPig read
    text = await _ocrService.ExtractTextAsync(stream, "application/pdf", ct);
}
```

The wiring is intentionally left to the follow-up task to avoid modifying
`PdfOrderParser.cs` in this scaffold PR.

## Cost estimate — Azure Document Intelligence prebuilt-read

Pricing (as of 2026-05; verify at https://azure.microsoft.com/pricing/details/ai-document-intelligence/):

| Tier | Price | Notes |
|---|---|---|
| Free (F0) | 500 pages/month free | Dev/test only; not for production |
| Standard (S0) | $1.50 per 1,000 pages | Up to 15 pages/transaction |
| Standard (S0) | $0.001 per additional page | Beyond 15 pages |

For ProcuLink's typical use case (single-page or short POs):
- A 1-page scanned PO costs ~$0.0015 (1.5 pages, billed in 15-page units at $1.50/1 000).
- At 1,000 scanned POs/month: ~$1.50.
- At 10,000 scanned POs/month: ~$15.00.

This is negligible compared to OpenAI mapping costs. The OCR path is only triggered
when PdfPig extracts no text (image-only PDFs), so real-world volume will be a small
fraction of total PO uploads.

## Known limitations

1. **Image-only PDF support only**: The Azure `prebuilt-read` call handles image-based
   PDFs. Text-based PDFs where PdfPig succeeds will never reach this service.

2. **No streaming**: The current implementation buffers the entire document into a
   `MemoryStream` before calling the SDK (`BinaryData.FromStream`). For very large
   scanned PDFs (>50 MB), memory pressure may be an issue. A future improvement
   could use `AnalyzeDocumentAsync` with a URL source (via R2 pre-signed URLs) to
   avoid buffering.

3. **Single-region**: The `Endpoint` config key points to a single Azure region.
   No retry or region-failover logic is implemented at this stage.

4. **No per-org usage tracking**: Unlike the OpenAI mapping path, OCR calls are not
   tracked against the per-org monthly token cap. This is acceptable at current
   volumes but should be revisited if OCR usage grows.

5. **No VCR cassettes / recorded responses in tests**: Tests only cover the no-op and
   `IsAvailable` contract. Live Azure integration tests are deferred.

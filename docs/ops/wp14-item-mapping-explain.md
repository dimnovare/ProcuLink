## What the founder is being asked to accept

The case-folded lookup gives up the unique `(org_id, supplier_id, buyer_item_code)`
index on its third column. What replaces it is **whatever the planner picks**, and
that is size-dependent: an index scan on `supplier_id` plus a filter at a few hundred
rows, a plain **sequential scan of `item_mappings`** at a few thousand, a bitmap heap
scan at hundreds of thousands. Earlier drafts of this PR asserted "not a sequential
scan"; the plans above show otherwise.

The scan is a COST fact only. The predicate is org+supplier scoped on every path, so
the rows returned are always one supplier's — tenancy does not depend on the plan.

The lookup runs ONCE PER ORDER (the batch resolver issues a single query for every
line), not once per line, which is what keeps the total bounded. The fix, if the cost
ever matters, is

```sql
CREATE INDEX CONCURRENTLY ix_item_mappings_org_supplier_lower_code
    ON item_mappings (org_id, supplier_id, lower(buyer_item_code));
```

which is DDL on a live production table and therefore the founder's call, not this
change's. It is deliberately NOT included in the PR.
